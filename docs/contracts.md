# Runtime contracts

Model connection recovery is bounded separately from action-format recovery. A typed provider outage with no HTTP status, originating from a connection failure before request dispatch, permits at most three same-route retries with 1/2/4-second backoff. The retry window is durably counted through archived history and resets only after a valid model response. Existing explicitly approved provider transitions retain precedence. Backoff checks cancellation, user pause, interruption and the original wall budget; it never extends that budget or replays an operation. HTTP failures, body failures, deadline expiry and requests with an uncertain dispatch outcome do not qualify. Receipts mark proven `request_dispatched:false`, retain absent usage as absent, and distinguish those attempts from unknown dispatched usage.

Observed metrics are read-only and cannot authorize completion. Provider-reported tokens, custom-endpoint estimates and legacy unclassified tokens remain distinct. Cached input is included within input; absent cache accounting is unknown. Live counters use durable projections across archival. Detailed reports replay receipts to derive complete accounting, current requirement evidence, acceptance freshness, operation outcomes and measured efficiency. Missing usage or timing disables an exact ratio; historical proof and public model narration do not become accuracy claims.

The task request, workspace path, provider, capability grants, budgets, and acceptance criteria are immutable once a run is created. A run has a stable UUID and one of `ready`, `running`, `paused`, `waiting_recovery`, `answered`, `completed`, `failed`, or `cancelled`. A client attachment is not the run: detaching or losing the terminal never changes the run state. Only a verified result with evidence may complete a milestone or the run. A tool-free conversational reply may end as `answered`, explicitly unverified, under the separate conversational contract below.

Both terminal follow paths give each newly spawned runner a separate three-second lock-acquisition grace period, including after a blocking question is answered. Polling during startup does not spawn duplicate children or reset that deadline. A child that never acquires its lock still ends the follow session as stopped; this does not discard the saved answer or change the durable task state.

An optional immutable `command_scopes` policy restricts `process.run` to exact program/argument-vector pairs. It narrows existing program grants, including `process:*`, and never grants access by itself. An empty command list denies every command; absent policy retains the existing program-level contract. Matching preserves case, order and argument boundaries without shell expansion or implicit flags. Kernel preflight rejects out-of-scope actions before intent creation; direct workers recheck the same policy before claiming an operation. Independent acceptance uses its separately frozen private check, not the agent's process grants. This is not a filesystem/domain sandbox for arbitrary programs or explicitly trusted-host MCP servers; those require their own reviewed isolation policy.

Container commands receive only explicitly selected environment values, including non-secret `ARUN_OPERATION_ID` and `ARUN_IDEMPOTENCY_KEY` from the durable intent. Command implementations may record these in external receipts and use the key for their own deduplication; the runtime does not claim that supplying a key makes arbitrary side effects exactly once. Host environment variables are not forwarded. Acceptance checks also get their own operation identity.

Container commands keep `/tmp` non-executable and provide only `/tmp/target` as a separate bounded executable tmpfs for compiled test artifacts. `CARGO_TARGET_DIR` points there. The container remains read-only outside authorized workspace mounts and tmpfs, with no network, dropped capabilities, resource bounds and no host credentials. An approved `process.run` or independent acceptance check can execute generated test binaries inside that boundary; `noexec` is not claimed for the whole container.

Every state change is committed with a monotonically increasing per-run event sequence. Events contain their type, timestamp, operation or model-turn ID where applicable, and a bounded JSON payload. A replay reads committed events and artifacts without calling the model or executing tools. Transactional projections preserve lifetime accounting and the next sequence across archival. A content-addressed recovery snapshot records the immutable contract fingerprint, checkpoint reference, milestones, activated versions, accounting, and unfinished operations. Recovery applies only its committed tail and verifies the result against current projections. The snapshot is a projection of the log, not a substitute for it: older audit details remain in integrity-checked artifact archives whose references and hot-row deletion commit together.

If a completed provider reply cannot be parsed as an Aegis action, including malformed JSON-encoded action arguments, no action is applied. When the provider supplied a usage receipt, the runtime records that failed attempt and makes at most one automatic format retry since the last accepted model action, subject to the same token and wall budgets. The retry prompt says no tool effect occurred; raw invalid provider text is not persisted or echoed. A second malformed reply, an interrupted turn, an unaccounted response, or a transport/body failure pauses instead of silently looping. Native tool calls and invalid output-item sequences are rejected independently. A completion receipt may precede its final output-item event; observed final actions must agree semantically with the receipt. Known completion usage is retained even when output-item validation rejects the response.

For an `invoke`, large file contents or scripts can use top-level `args_text_field` (`content` or `script`) and `args_text`. That selected key must be omitted from `args`; the parser inserts the text into the decoded argument object before normal capability/schema/grant validation. This removes the second JSON escape layer for code without changing execution authority. A conflicting key, orphan text, invalid selected field or use on a different action is rejected. Legacy action arguments remain supported. Empty unused text fields are part of the strict provider schema.

Provider request serialization orders the action schema's properties with `kind`, `capability`, text selector and text payload before encoded arguments. Only the two provider schema locations are reordered; arbitrary task data, persisted JSON, contract fingerprints and parsing/authorization rules retain their existing semantics. Rejected-action diagnostics can retain character counts, recognized text selectors and fixed JSON error categories/positions, never the rejected argument text or parser message.

Responses assistant items marked `phase: commentary` are intermediate updates; only the `final_answer` action is applied. Legacy responses without phase metadata remain supported. See [OpenAI's phase guidance](https://developers.openai.com/api/docs/guides/reasoning). Two identical serialized action objects may be normalized to one action; distinct actions, extra objects, truncated JSON and surrounding prose remain rejected.

MCP progress messages are correlated with the actual tool request token and stored as bounded `operation.output` previews. The client queues at most 16 messages, each limited to 8 KiB, and emits at most 64 KiB or 128 messages per call with a truncation indication. UTF-8 characters are not split. These messages are excluded from model context and cannot prove completion; only the final tool result can produce execution evidence. The native Windows helper streams retained stdout/stderr through this path without changing tool authority or final receipt limits.

A model failure pause distinguishes an explicit user interruption, expiration of the original task wall budget, expiration of the allocated model response deadline, and earlier provider unavailability. Deadline classification uses elapsed time and the original budget. It grants no extra time, automatic transport retry or unrecorded usage.

An explicit user pause is persisted and acknowledged only at a safe action boundary, saving a checkpoint before inference stops. Resume preserves the original run and accounting. The execution deadline and `/budget` exclude intervals between a safe `run.paused` boundary and resume. Waiting for the current action to finish still consumes time. Resume never resets or increases the original allowance. The durable pause clock survives archival, migration and restart; terminal execution time remains fixed.

Original task-owner messages covered by working-memory summaries remain in subsequent prompts independently of those summaries. A summary cannot remove or supersede owner constraints; later owner corrections take precedence. Repeated character runs can use a lossless segment encoding, and ordinary text remains verbatim. The existing overall context limit remains enforced; owner text is never silently clipped to make a summary fit.

Visual receipt lookup uses a per-run index and reads at most nine candidates, with at most eight unmarked legacy receipts inspected. Normal requests never replay event archives or load every operation to find images. Existing runs build the index once from integrity-checked history. A malformed image in an intact receipt is quarantined with a persistent model-facing diagnostic; the model can ask for a replacement or capture a new image. Older screenshots are not substituted for the rejected source. A new valid image replaces it. Artifact integrity errors continue to stop recovery.

Live workspace diffs stream complete UTF-8 chunks of at most 64 KiB, retaining a full diff artifact and chunk offsets. Subsequent changes continue throughout the operation, including after 128 updates. File, scope and snapshot limits remain enforced; these observations never prove execution or completion.

`process.run` receipts require an integer exit code of zero to succeed. Nonzero or absent exit status records a failed operation with an inspectable receipt, which cannot verify obligations or complete work. Repeated equivalent failures count toward the durable stall guard even when retry arguments change; new owner input or observed workspace progress starts a new observation epoch.

The durable exploration guard records returned evidence rather than successful action arguments. Workspace and capability searches compare individual results across queries, orderings and subsets. File reads track Unicode character coverage per path and content hash, so overlapping known ranges add no information. Inspections compare their actual returned excerpts; empty, invalid and past-end selections add none. Timing metadata and model-authored maintenance prose cannot establish progress. These deterministic comparisons detect repeated evidence; they do not certify semantic relevance to the user's goal.

Both evidence-backed completion and conversational replies recheck the task-owner mailbox inside the terminal transaction. Messages arriving after the last model request must reach a subsequent request before the task can end.

An operation has a stable ID, capability version, validated arguments, idempotency key, side-effect class, deadline, and state. Its transitions are `pending -> dispatched -> executing -> succeeded | failed | timed_out | cancelled | outcome_unknown`. Before acting, a worker takes an operation lock, rechecks grants/schema/version, and atomically claims a dispatched operation. A second adapter process cannot repeat a claimed operation, including the gap after the first worker exits but before the kernel commits its result. The intent and `pending` event commit before dispatch; a durable artifact is written and synchronized before the result event references it. A timeout does not establish that an external side effect did not happen.

On restart, an operation without a terminal outcome is reconciled. A read-only/idempotent operation may be repeated with the original idempotency key. An externally queryable operation checks the external system first. A non-idempotent operation whose outcome cannot be queried becomes `outcome_unknown`, pauses the run, and requires explicit reconciliation; it is never blindly retried. The worker enforces the kernel's grant and deadline, not merely the model-visible manifest.

## Evidence and result mapping

Model-authored milestones record past progress, rather than current requirement verification. A completed plan step needs intact evidence from a successful operation in the same run; later edits do not erase that historical progress. All custom plan steps must be completed before finishing. The separate immutable obligation ledger and every final completion artifact still require evidence from the current workspace revision, with independent acceptance enforced when configured. Historical plan evidence cannot satisfy those gates.

User-approved repository guidance freezes exact UTF-8 content, source path, directory scope, SHA256 and review revision into new contracts. The approved source must still match on task creation; changed/missing files require explicit review/removal. Guidance inaccessible under the run's read grants/scopes is excluded. Root sources are offered through the terminal; nested sources are explicitly selected, not recursively crawled. At most eight reviewed files / 16384 UTF-8 bytes (body/path/scope), with an 8192-byte per-file body limit, are stored. Unsafe text and oversize files are rejected rather than summarized or truncated. Approval does not grant tools or completion evidence; stored source text remains outside the rolling event context. Existing runs never reread changed files as trusted guidance.

Model-facing event payloads are JSON objects rather than JSON strings containing another encoded JSON document. Ordinary events keep their bounded summary; explicitly selected artifact/chat excerpts keep their separately bounded content. This avoids repeated escaping without expanding retrieval authority or changing evidence. A regression checks both serialized bytes and pinned tokenizer units; it does not establish lower native-provider billing or comparative task efficiency.

The discoverable `workspace.read_batch` capability uses the existing `workspace.read` grant and accepts up to eight ranges, including distinct offsets of the same file. Each requested length is 1..65536 Unicode characters; actual selected text is automatically paginated at 65536 characters across the batch, in request order. Short files consume only their actual text. Later ranges may receive empty text when the output budget is exhausted; their unchanged `next_offset` explicitly identifies where to continue. Paths are checked before intent and rechecked before worker claim, even without narrowed file scopes. Sources must be regular UTF-8 files at most 2 MiB; metadata/link traversal is rejected. Artifacts contain bounded selections, whole-file SHA256, offsets and total character counts under a 524288-byte serialized-result bound. Recent selected batches enter context directly; a bounded historical read index retains older range/artifact metadata through event archival. Historical metadata does not prove a file is unchanged. `workspace.search` optionally limits its literal query to one checked exact relative file. Existing context reservation and grants remain authoritative; no effectful batch/retry policy is introduced.

In artifact/durable modes, a successful `workspace.read` also maps complete content into the next context when the committed result contains at most 65536 Unicode characters. The artifact/evidence handle is retained, an available valid SHA256 is preserved, and `complete: true` distinguishes complete bounded file content from excerpts. It never rereads the current workspace for this mapping, imports file text as guidance, or turns a large truncated prefix into complete content. Larger results keep the artifact-backed path; bounded selected ranges remain available through read_batch. Eager/lazy baseline inline-result behavior is unchanged. Automatic file text is included in the same before-request normalized tool-context reservation, not free or unaccounted tokens.

A successful `workspace.write` immediately reads back the written file and returns its SHA256. For at most 1024 Unicode characters it also stores the verified complete text in the result artifact, which artifact/durable modes map into the next model context with `complete: true` and the operation evidence handle. Larger writes retain the digest/handle without automatic full text. This does not promise the file cannot change later or force the model to skip a fresh read; it makes the just-committed small result available without another inspection turn. Its mapped text consumes the same before-request tool-context budget.

Artifact inspection maps explicitly requested text into the next bounded inference context rather than applying ordinary tiny event-summary truncation. An empty query returns the first 4,000 Unicode characters; `@slice offset length` selects zero-based characters with length 1–4,000, and `@lines first count` selects one-based lines with count 1–100 and at most 4,000 output characters. Other queries perform literal line matches; `@find text` escapes reserved prefixes. Structured file/MCP text is decoded before indexing. At most twelve recent events are assembled; repeated mapped excerpts are measured and reserved against the frozen normalized tool-context budget before another provider request. Whole files, transcripts and raw large outputs are not implicitly mapped.

Literal search shows bounded text around the first match in each matching line, rather than always showing its prefix. A clipped leading excerpt reports its zero-based Unicode character offset for follow-up slices. Content stays at most 300 characters per matching line, twenty matching lines and 4,000 total output characters; line numbers, clipping markers and offsets are metadata within that total. Case-insensitive search does not reinterpret the query as a regular expression.

An MCP result with `isError: true` is a reported failed operation, with its result artifact preserved for inspection. It cannot be used as successful milestone/completion evidence. A transport crash after unsafe dispatch remains outcome-unknown rather than being confused with an acknowledged tool error. Observers drain committed final events after seeing terminal state, preventing a concurrent completion commit from disappearing from the normal terminal feedback.

## Independent acceptance

An optional acceptance check is validated and copied into the immutable task contract. A completion proposal is written to a durable artifact before the kernel dispatches `runtime.acceptance`; this private capability is not model-discoverable or grantable through tool manifests. The worker verifies the proposal, configured check version, and evidence before claiming it. Checks execute with a read-only workspace, no container network, a bounded deadline/output, and hidden runtime metadata. Assertion code embedded in the approved arguments remains frozen even if the workspace's original configuration file changes.

Nonzero check exits reject completion and expose bounded failure evidence for the next model turn. An unavailable environment pauses instead of claiming success. On restart, an unfinished read-only verification may safely retry; a recorded passing result completes its original proposal without another model call. The storage completion gate rejects missing checks, failed results, or a summary/evidence set different from the checked proposal. Its acceptance artifact and resolved proposal commit with the terminal state. Checks that invoke mutable workspace test files must additionally use their own integrity assertions; freezing command arguments does not freeze every file an approved command might read.

## Crash cases

1. Crash after intent commit and before worker dispatch: restart sees `pending`; the durable dispatch/claim gate proves no adapter executed this intent, so it can dispatch once even when its eventual effect is unsafe. Once the operation is `dispatched` or `executing`, that proof no longer holds.
2. Crash after external side effect and before result commit: restart sees `dispatched`; it queries external state or pauses. It must not duplicate an unsafe side effect.
3. Crash after artifact write and before result commit: the artifact may be orphaned. Recovery treats the operation as unresolved and cleanup may remove unreferenced artifacts; no event may reference missing bytes.

## Evaluation contract

Use the same model, prompts, tool implementations, grants and elapsed-time limits for paired runs. Treat model and tool token totals as measured outcomes, not task caps. Compare eager schemas, lazy discovery, lazy plus artifact-backed context, and the durable runtime. Registry sizes: 50, 100, 250, and 500, with overlapping names and deliberately irrelevant capabilities. Record schema tokens, total model tokens, wrong-tool choices, invalid arguments, elapsed time, completion against external acceptance tests, duplicate side effects, and recovery time; report paired observations and uncertainty, not invented targets.

Initial tasks: locate a symbol among similarly named repository search tools; identify a failing test from a large compiler log by inspecting a slice; repair a small repository under an acceptance test; interrupt a read-only operation before its result; interrupt a non-idempotent external operation after dispatch; restart after artifact creation before event commit. A baseline is reproducible only when task fixtures, tool registry, model/version, seed where supported, budgets, and raw event logs are saved.
# Conversational replies

The existing `finish(summary, evidence)` action with empty evidence ends a tool-free conversational turn as `answered`, not `completed`. It is rejected after any operation, a custom milestone plan, or a configured independent acceptance check. A reply is durable conversation context, never successful-operation evidence or an independently accepted learning example. Greetings and explanations must not create files merely to satisfy the tool-work completion gate. Evidence-backed work retains its original completion and acceptance requirements.
