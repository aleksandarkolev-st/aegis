I’d build Aegis around a **local-authority + cloud-relay + channel-adapter** architecture.

The important decision is this: **WhatsApp/iMessage must never become part of the trusted execution layer.** They are remote control surfaces. Aegis on the user's machine remains the authority.

```text
                         INTERNET
                             │
              ┌──────────────┴───────────────┐
              │                              │
         WhatsApp                       iMessage
              │                              │
     Evolution API /                 platform-imessage
     Meta Cloud API                   on user's Mac
              │                              │
              └────────────┬─────────────────┘
                           ▼
                 ┌──────────────────┐
                 │ Aegis Relay      │
                 │                  │
                 │ Identity/routing │
                 │ Pairing          │
                 │ Notifications    │
                 │ Delivery only    │
                 └────────┬─────────┘
                          │
                    NATS JetStream
                          │
                   outbound TLS only
                          │
                          ▼
              ┌────────────────────────┐
              │ aegis-remote daemon    │
              │ USER'S COMPUTER        │
              └────────────┬───────────┘
                           │
                           ▼
                 ┌─────────────────┐
                 │ AEGIS KERNEL    │
                 │                 │
                 │ SQLite log      │
                 │ permissions     │
                 │ obligations     │
                 │ evidence        │
                 │ operations      │
                 │ model           │
                 └────────┬────────┘
                          │
                          ▼
                     workspace
```

That is the architecture I would choose.

The reason it fits Aegis particularly well is that Aegis already has the right local primitives. Its current storage layer treats runs, events and operations as durable state, with operation idempotency keys and an append-style event sequence. Remote control should feed into that system rather than create a second task system in the cloud.

### 1. Aegis stays local and authoritative

This is the most important rule.

The cloud must never contain functionality equivalent to:

```text
shell("rm ...")
write_file(...)
git_push(...)
approve_anything(...)
```

Instead it can only deliver something like:

```json
{
  "command_id": "cmd_01H...",
  "installation_id": "devbox_a83c",
  "actor": {
    "channel": "whatsapp",
    "id": "..."
  },
  "run_id": "run_184",
  "kind": "approve_operation",
  "payload": {
    "operation_id": "op_91",
    "scope": "once"
  },
  "expires_at": 1790800000
}
```

Aegis locally receives it and decides:

```text
Does op_91 exist?
Is it still pending?
Does it belong to run_184?
Is this remote user authorized?
Has cmd_01H already been processed?
Can this type of approval be done remotely?
Has it expired?
```

Only then does anything happen.

That preserves the core property that makes Aegis interesting.

---

### 2. Add `aegis-remote` to the native binary

I would not create an entirely separate runtime.

Add something approximately like:

```text
src/remote/
    mod.rs
    protocol.rs
    client.rs
    identity.rs
    pairing.rs
    policy.rs
    inbound.rs
    outbound.rs
```

The daemon can run as:

```text
aegis remote start
```

or automatically alongside interactive Aegis.

Its connection is always:

```text
computer ─────OUTBOUND─────> relay
```

Never:

```text
internet ─────> :8080 on user's computer
```

This means:

- no router configuration,
- no port forwarding,
- works behind CGNAT,
- works on hotel/Wi-Fi networks,
- dramatically smaller attack surface.

---

### 3. Use NATS JetStream between relay and Aegis

After looking at the alternatives, I think NATS fits this better than implementing your own WebSocket queue.

JetStream already gives you acknowledged publishing, durable consumers, replay, redelivery and message deduplication capabilities, and there is an official Rust `async-nats` client with JetStream support. :chatgpt-content-reference{index="0"}

Conceptually:

```text
aegis.device.7FH2.commands
aegis.device.7FH2.events
```

Commands:

```text
cloud → aegis
```

Events:

```text
aegis → cloud
```

For example:

```text
commands:
  message
  approve
  deny
  pause
  resume
  cancel
  select_task
```

and:

```text
events:
  task_started
  progress
  approval_required
  blocked
  task_completed
  task_failed
  reply
```

But there is a critical distinction:

**JetStream is not the source of truth.**

It is only the reliable transport.

Aegis's local SQLite database remains authoritative.

So if NATS delivers a command twice:

```text
approve op_91
approve op_91
```

Aegis sees the same `command_id` and the second becomes a harmless duplicate.

That complements the existing Aegis operation/idempotency design very well.

---

### 4. Keep the cloud relay deliberately stupid

I would write a small service:

```text
aegis-relay
```

Its responsibilities should be only:

```text
channel webhook
       ↓
authenticate sender
       ↓
resolve installation/account
       ↓
normalize message
       ↓
publish command
```

And the opposite direction:

```text
Aegis event
      ↓
resolve notification destination
      ↓
format for WhatsApp/iMessage
      ↓
send
```

It may store:

```text
users
installations
channel_bindings
pairing_tokens
delivery_receipts
notification_preferences
```

It should **not** store:

```text
repository contents
model context
shell output
provider access tokens
workspace credentials
complete Aegis event logs
```

For a hosted Aegis product I'd use PostgreSQL for this metadata.

## WhatsApp

For WhatsApp I would put a channel abstraction in front:

```text
trait MessagingChannel {
    receive()
    send()
    send_attachment()
    capabilities()
}
```

Then implement:

```text
WhatsAppCloud
WhatsAppBaileys
IMessage
...
```

For initial development, Evolution API is attractive because it already provides REST/event integration and supports both Baileys-based WhatsApp Web and Meta's official WhatsApp Cloud API. :chatgpt-content-reference{index="1"}

That means you could develop cheaply with:

```text
Evolution → Baileys
```

and later run:

```text
Evolution → official WhatsApp Cloud API
```

without changing the Aegis protocol.

However, I would **not make Evolution API a fundamental Aegis dependency**. Keep it behind an adapter.

Its current licensing is Apache-2.0-based but includes additional branding/usage-notification conditions, which is another reason not to entangle your core architecture with it. :chatgpt-content-reference{index="2"}

Eventually you may decide that the official Meta API is simple enough to talk to directly.

---

## iMessage

For iMessage, I would use **Beeper's `platform-imessage`** rather than build anything involving Messages internals yourself.

It:

- sends and receives iMessages,
- receives realtime updates,
- supports attachments/replies/reactions,
- runs with SIP enabled,
- uses the normal logged-in Messages account,
- doesn't rely on a separate network service,
- is MIT licensed. :chatgpt-content-reference{index="3"}

And there's a particularly useful architectural consequence:

Because Aegis already has its own relay, you **don't need BlueBubbles' relay layer**.

Run:

```text
platform-imessage
        │
        ▼
Aegis iMessage adapter
        │
        ▼
Aegis remote protocol
```

The limitation is important: `platform-imessage` runs on **macOS only**. :chatgpt-content-reference{index="4"}

Therefore:

```text
Mac user:
Aegis + iMessage adapter on same computer
```

works naturally.

But:

```text
Windows gaming PC + iPhone
```

cannot magically gain native iMessage support. The user would need an authenticated Mac somewhere acting as the Messages bridge.

I would treat iMessage support as optional for exactly that reason.

---

## Pairing

The user shouldn't type passwords into WhatsApp.

Do this:

```text
$ aegis remote pair whatsapp

Pair your WhatsApp account:

Send:
AEGIS 7Q4M-KP9D

to:
+1 xxx xxx xxxx

Expires in 5 minutes.
```

The user sends:

```text
AEGIS 7Q4M-KP9D
```

The relay consumes the token once and creates:

```text
(channel=whatsapp,
 sender=whatsapp-user-X)
           ↓
installation=7FH2
```

After that the channel identity becomes an authenticated remote principal.

For iMessage the same mechanism works.

## Remote permissions need a separate policy

This is where I would make Aegis materially safer than most remote-agent products.

Remote access should **not inherit every local control**.

For example:

| Action | Phone |
|---|---|
| ask Aegis something | yes |
| start task in already-approved workspace | yes |
| status | yes |
| pause | yes |
| resume | yes |
| cancel | yes |
| approve ordinary pending operation | yes |
| read bounded evidence | yes |
| change model | perhaps |
| grant a new directory | no |
| reveal secrets | no |
| add credentials | no |
| expand network access | no |
| disable safeguards | no |
| arbitrary shell command | no |
| change remote security policy | no |

This protects against the worst-case scenario:

> someone steals/unlocks your phone or WhatsApp account.

They should not be able to message:

```text
Aegis give yourself access to C:\
upload my SSH keys
```

and have it work.

The local task contract remains stronger than the remote user interface.

---

## Approval messages

Make approvals strongly bound to an existing operation.

Not:

```text
Aegis:
Run npm install?

You:
yes
```

internally.

Instead the user sees friendly text, but the reply resolves to:

```text
approval:
    run_id: run_184
    operation_id: op_8B2
    challenge_id: approval_B91
    expires: +10 minutes
```

Then:

```text
Approve once
```

can only approve that exact pending operation.

It cannot become a generic `"yes" → permission=true`.

This is important.

---

## Chat/task mapping

WhatsApp doesn't naturally have the task/session semantics that Aegis has.

I would therefore make a chat bind to a **selected Aegis task**.

Example:

```text
You:
Fix the login tests

Aegis:
Started #184 · auth-service
I'm working on it.
```

Further normal messages go to `#184`.

```text
You:
Don't change the database schema.
```

becomes a follow-up to `#184`.

If you type:

```text
tasks
```

Aegis replies:

```text
#184  Auth tests        running
#181  Payment refactor  paused
#176  Add metrics       completed

Reply "use 181"
```

Then:

```text
use 181
```

changes the chat binding.

This is much cleaner than trying to guess which task every message refers to.

---

## Notifications

Don't stream the terminal into WhatsApp.

Send **state changes**, not noise.

Good:

```text
Aegis

Checkout refactor needs approval.

→ npm test
→ estimated max runtime: 4m
→ no network access requested

Reply:
1 Allow once
2 Deny
```

Good:

```text
Aegis

Checkout refactor completed.

✓ 4/4 requirements
✓ 83 tests passed
✓ no new dependencies

Reply "details" for evidence.
```

Bad:

```text
Reading foo.rs...
Reading bar.rs...
Thinking...
Executing...
Thinking...
```

Aegis already has an event model. The notification service can simply reduce those events to meaningful transitions.

---

## Borrow from Beeper, don't adopt Matrix

I changed my view slightly after examining Beeper's new `ai-bridge`.

There is a lot worth stealing conceptually.

Their AI bridge already models:

- resumable AI sessions,
- streaming events,
- tool-call events,
- human approvals,
- rich structured AI messages,
- chat rooms bound to persistent sessions. :chatgpt-content-reference{index="5"}

Their protocol design is worth studying closely.

But I would **not make Aegis a Matrix application**.

You'd be introducing:

```text
Synapse
Matrix rooms
appservices
bridgev2
Matrix identities
Matrix media
Matrix state
```

to solve something that Aegis can represent much more directly.

Beeper benefits because its entire product already speaks Matrix. Aegis doesn't.

So:

```text
Borrow:
AI event format
approval concepts
streaming semantics
session/message lifecycle
```

but not:

```text
Matrix as Aegis's core transport
```

# Final architecture

If I were implementing this in Aegis now, my stack would be:

```text
                     CHANNEL LAYER

WhatsApp                          iMessage
   │                                 │
Evolution API                  platform-imessage
then official Meta             macOS only
   │                                 │
   └──────────────┬──────────────────┘
                  │
                  ▼

               AEGIS RELAY
           Rust / lightweight service
           PostgreSQL metadata
                  │
                  ▼
              NATS JetStream
          durable command/event bus
                  │
                  │ TLS outbound
                  ▼

         aegis remote daemon
              async-nats
                  │
                  ▼

             AEGIS CORE

       SQLite = source of truth
       kernel = authority

       Runs
       Events
       Operations
       Obligations
       Permissions
       Evidence
       Idempotency
```

NATS is particularly suitable here because JetStream already supplies the reliable-delivery mechanics while `async-nats` fits directly into Aegis's existing Tokio/Rust stack. :chatgpt-content-reference{index="6"}

The cloud is disposable.

If the entire relay disappears for a day:

```text
Aegis keeps running locally.
```

When connectivity returns:

```text
relay reconnects
notifications resume
commands redeliver
```

The task itself was never living in the cloud.

That property is exactly what I'd preserve.

### What I would build first

I would implement only this initial vertical slice:

1. `aegis remote` with an outbound JetStream connection.
2. A tiny relay.
3. WhatsApp only.
4. Pairing.
5. `message`, `status`, `pause`, `resume`, `cancel`.
6. `approval_required` + `approve_once`/`deny`.
7. `completed`/`failed` notifications.
8. Strict remote permission policy.

Then add iMessage as another adapter.

I would **not** start with attachments, remote terminal access, diffs, provider configuration, Matrix, multiple Aegis hosts, voice messages, group chats or elaborate buttons.

If that first version feels excellent, everything else has a clean place to attach.

The core architectural principle is:

> **The phone can tell Aegis what you want. Only the local Aegis kernel can decide what that is allowed to cause.**

That keeps the feature aligned with what makes Aegis different rather than turning it into a generic chatbot connected to a shell.
